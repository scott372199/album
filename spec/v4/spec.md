## 1. 目标

v3 结束时，这个站已经「好看、能讲、能当照片墙」。但它仍然只是一件**只能从这台 Mac 发布**的作品：照片靠数据线拷进 `photos/`，构建靠本机恰好装着 sharp 和 ffmpeg，发布靠本机配好的 AWS CLI，基础设施靠一堆命令式脚本和 `.deploy-state.json` 里的运行时 ID。

v4 **不再动视觉**（视觉已在 v3 验收），转向三件使用方式与工程上的事：

1. **走得到**：加一个安卓客户端，能在自己的手机上打开这个相册。目标机型是国产手机（荣耀 / 华为 / 三星 / 小米），私有分发，不上任何应用商店。
2. **加得进**：拍完照直接在手机上选中上传，服务端自动转码、脱敏、上线，不必回到电脑。
3. **重建得出**：整套 AWS 基础设施用 Terraform 声明化——分层的代码架构、可复用的模块、按环境注入的参数，**代码托管在一个独立的私有仓库**里。换一台机器、克隆仓库、填好参数，就能把整套环境重建出来。

**成功标准**

- 在荣耀/小米/三星任一台安卓手机上装好 APK，点开图标即进入相册；全屏无浏览器地址栏，返回键行为正确（灯箱打开时先关灯箱）。
- 在手机上从系统相册选 5 张照片上传，**一分钟内在网页端能看到**（含缩略图与灯箱大图），且浏览器开发者工具里这些图的响应**不含 EXIF**。
- 手机上传的视频同样在数分钟内可播（1080p / ≤30s / 无原始元数据）。
- App 启动时能发现新版本并完成更新安装，无需连电脑。
- **在任意一台干净机器上**：`git clone` 基础设施仓库 → 填入参数 → `plan` 输出**为空**（说明线上每一份资源都被代码完整描述）；`apply` 能从零建出同等环境。
- **基础设施代码与应用代码分仓**：两边提交历史互不干扰；基础设施仓库里没有照片、没有前端产物、没有 state 文件。
- **合并即上线**：改完前端代码合并到主分支，5 分钟内自动完成构建、部署、CDN 失效与线上自检，不需要人工执行任何命令。
- **基础设施不被顺手改掉**：`plan` 自动跑出来给人看，但 `apply` 必须由本人点头。改错了断不了站。
- 隐私五条不变量仍逐字成立：产物不含 GPS / 序列号 / 原始文件名 / 具体拍摄时刻；照片不裁切、不加滤镜。
- 成本仍 ≤ ¥15/月。

## 4. 功能需求

### FR-19 安卓客户端（WebView 壳）【新增】

**形态结论：WebView 壳，不是 TWA、不是原生重写。** 依据见 §11.2。

- **FR-19.1 渲染**：用系统 WebView 加载 `https://photos.chenyouyi.top/`。不依赖 Google 服务、不依赖用户安装 Chrome。
- **FR-19.2 全屏**：edge-to-edge 沉浸式，状态栏透明、无地址栏、无浏览器 UI。
- **FR-19.3 返回键**：先交还给页面（由页面处理灯箱/故事/照片墙的关闭），页面无可关闭层级时才退出 App。
- **FR-19.4 选图上传**：支持网页内的文件选择（系统相册选择器），多选，界面上可见上传进度与结果。
- **FR-19.5 屏幕常亮**：照片墙模式下不熄屏，退出该模式后恢复系统行为。
- **FR-19.6 断网**：加载失败时显示一页明确的离线提示与「重试」，**不做离线浏览**（见 O-04）。
- **FR-19.7 兼容降级**：WebView 内核对 CSS 滚动驱动动效、`View Transitions` 的支持参差。**不支持时必须回退为「元素直接可见」**，绝不允许出现停在半透明起始帧的内容。
- **FR-19.8 配置**：站点地址、版本号可配；除密钥外的环境值不硬编码在逻辑里。

### FR-20 私有分发与应用内更新【新增】

- **FR-20.1 签名**：自签 keystore，一次生成长期使用，**密钥与口令不进仓库**，由用户离线备份。丢失即无法覆盖升级。
- **FR-20.2 下载**：提供稳定的私有下载地址（形如 `https://photos.chenyouyi.top/apk/…`），能直接在手机浏览器点开安装。
- **FR-20.3 应用内更新**：启动时检查新版本 → 提示 → 下载 → 调起系统安装器。全程不需要连电脑。
- **FR-20.4 国产 ROM 引导**：安装被「纯净模式 / 未知来源」拦截时，给出该厂商的开启路径说明，而不是只报一个失败。
- **FR-20.5 不上商店**：不提交 Google Play 或任何国内应用市场，不做商店素材与审核材料。

### FR-21 手机端上传与鉴权【新增】

- **FR-21.1 身份**：手机号 + 共享密钥组合登录，换取短期令牌。使用者为个位数，**不引入用户注册体系**。
- **FR-21.2 白名单**：只有登记过的手机号能登录；白名单与密钥不在代码与仓库中。
- **FR-21.3 直传**：照片/视频由手机直接上传到私有源桶，不经过应用服务器中转（避免大小限制与费用）。
- **FR-21.4 上传前处理**：手机端把 HEIC 等格式转为 JPEG（保持原始像素尺寸，仅格式转换）；视频原样上传。理由见 §11.5。
- **FR-21.5 配额**：单次最多 20 个文件；单张图片 ≤ 30MB，单个视频 ≤ 200MB。超限时在选图后立刻提示，不浪费流量。
- **FR-21.6 归属**：上传时选择目标相册（已有相册 + 新建），未选择时进「未分类」。
- **FR-21.7 时间**：拍摄时间优先取手机媒体库记录，缺失时由服务端读 EXIF，再缺失则用上传时间。**只有年月会进入公开产物**。
- **FR-21.8 可见反馈**：每张照片有「上传中 / 处理中 / 已上线 / 失败」四态，失败可重试。

### FR-22 服务端转码与增量发布【新增】

- **FR-22.1 触发**：源桶出现新对象即自动处理，无需人工干预。
- **FR-22.2 图片**：生成 `thumb.webp`（320w）与 `view.webp`（2048 长边），与 v3 规格一致；**输出必须不含任何 EXIF**。
- **FR-22.3 视频**：转 H.264 / 最长边 1920 / ≤30s / crf23，剥离全部元数据；转码失败则降级为只留封面。
- **FR-22.4 发布**：产物写入站点桶（内容哈希文件名），更新清单与版本文件，并让 CDN 上的入口页与版本文件失效。
- **FR-22.5 幂等**：同一内容重复上传不产生重复条目（沿用内容哈希去重）。
- **FR-22.6 延时**：图片从上传完成到网页可见 ≤ 60 秒；视频 ≤ 5 分钟。
- **FR-22.7 失败可见**：处理失败进入死信队列，不得出现「清单里有一张打不开的图」。

### FR-23 站点侧改造【重写】

- **FR-23.1 manifest 运行时装载**：页面不再依赖构建时注入的清单，改为先取版本文件、再按其中文件名取清单。这样服务端增量发布才能生效。
- **FR-23.2 构建拆分**：
  - `build:web` —— 只产出前端静态资源，**不读 `photos/`**。任何机器上结果一致。
  - `build:all` —— 本地全量：扫 `photos/` + 转码 + 生成清单，用于首次导入与灾后重建。
  - 拆分理由：让「改代码」与「加照片」两条路径彻底解耦。改代码时不该要求几百张照片在场，加照片时也不该重新编译前端。
- **FR-23.3 上传入口**：仅在已登录的客户端内显示；公开网页端不出现上传按钮。
- **FR-23.4 动效守卫**：对滚动驱动动效与 View Transitions 做能力检测，不支持时退化为全可见（同 FR-19.7）。
- **FR-23.5 行为不变**：时间轴、相册、筛选、灯箱、故事、照片墙的交互与视觉**与 v3 保持一致**。

### FR-24 Terraform 分层基础设施即代码【新增 / 重写部署方式】

#### 24.1 代码架构：分层

按**变更频率与爆炸半径**分层。每层是独立的 Terraform 根，各自独立 state，层与层之间只通过输出变量传递 ID：

| 层 | 职责 | 区域 | 为什么单独成层 |
| --- | --- | --- | --- |
| **L0 bootstrap** | 状态存储（远端 state 桶 + 锁表）、部署身份 | 主区域 | 只需执行一次；不能由「需要它自己才能运行」的配置来管理 |
| **L1 storage** | 站点桶、源桶、下载桶、桶策略、加密、版本控制、生命周期 | ap-southeast-1 | 变更低频，是其他三层的数据底座 |
| **L2 edge** | CloudFront 分发、OAC、缓存策略、路径行为 | us-east-1（含全局资源） | 风险最高（配错即断站），必须能单独把关；区域也与其他层不同 |
| **L3 compute** | 镜像仓库、处理函数、HTTP 接口、消息队列、参数与密钥、相关 IAM | ap-southeast-1 | 变更最频繁（业务逻辑载体） |

- **FR-24.1.1** 层间依赖单向：`bootstrap → storage → edge → compute`。不允许循环引用，不允许跨层直接改写对方资源。
- **FR-24.1.2** 每层独立 `plan`，出错时影响面可控。
- **FR-24.1.3** 层内可再拆模块（见 24.2）；模块实例不在层间共享。

#### 24.2 模块化

- **FR-24.2.1** 可复用单元抽成模块，至少覆盖：私有静态桶、CDN 站点、容器化函数、HTTP 接口、参数存储、桶事件通知。
- **FR-24.2.2** 模块只接受参数、只产出输出，**不得内含环境值字面量**（桶名、账号、域名一律由调用方传入）。
- **FR-24.2.3** 模块来源的原则：**凡需精确接管既有资源的（尤其 CDN 分发），直接写资源或写极薄模块，不套用厚封装的社区模块**——厚封装无法把 `plan` 调到为空。全新资源的层优先复用成熟社区模块，避免重造轮子。
- **FR-24.2.4** 每个模块必须有带 `type` / `description` / `validation` 的变量声明，以及输出声明。

#### 24.3 参数化

- **FR-24.3.1** 环境相关值（区域、域名、桶名、镜像 tag、并发上限、保留天数等）**全部走变量**，代码中不得出现字面量。
- **FR-24.3.2** 变量分层：通用默认值写在变量声明里；环境值写在该层目录下的参数文件；**敏感值不进参数文件**，走密钥管理服务引用。
- **FR-24.3.3** 每个变量必须有 `description` 与 `type`；关键取值加 `validation`（区域白名单、域名格式等）。
- **FR-24.3.4** 后端配置（state 位置）也用参数化文件描述，不写在 `backend` 块内部。
- **FR-24.3.5** 输出变量必须写明用途供下游引用；敏感输出标记为敏感，避免出现在日志。

#### 24.4 仓库与边界

- **FR-24.4.1 独立仓库**：IaC 代码托管在**新的独立私有仓库**，与应用仓库（`album`）分离。理由：内容含账号 ID / 分发 ID / 桶名等资源标识，公开即暴露攻击面；且基础设施与应用变更节奏不同，混仓后历史无法阅读。
- **FR-24.4.2 私有**：仓库必须私有。不得出现照片、前端产物、APK、镜像二进制、state 文件。
- **FR-24.4.3 应用仓库保留什么**：前端与处理函数的源码、构建脚本、结构断言。**处理函数源码留在应用仓库**（代码属应用），基础设施仓库只声明镜像仓库与函数，镜像 tag 作为参数传入。
- **FR-24.4.4 不得双源**：同一份配置不得既存在于 Terraform 又存在于旧脚本（见 24.8）。

#### 24.5 迁移与接管

- **FR-24.5.1** 现有资源（站点桶、OAC、CloudFront 分发、证书）必须**导入**，不得重建。
- **FR-24.5.2** 分步接管，每步以「`plan` 为空」为通过条件；任何非空差异须逐条解释清楚才可继续。
- **FR-24.5.3** 导入顺序按层：L1 storage 先（低风险），L2 edge 次（最高风险），L3 compute 最后（全新资源）。L0 先于一切。
- **FR-24.5.4** 证书只导入不重建（依据 §11.9）。
- **FR-24.5.5** 每一步迁移都要有可回退方案，且回退后线上仍可访问。

#### 24.6 安全与规范

- **FR-24.6.1** 状态文件加密存放，且**状态里不得出现明文敏感值**（敏感值走密钥管理引用）。
- **FR-24.6.2** 部署身份按最小权限授予；不得使用账号根凭证。
- **FR-24.6.3** 提交前必须通过格式与语法校验，不能只靠人眼。
- **FR-24.6.4** 仓库内提供一份资源清单说明（每层管什么、谁引用谁），供日后阅读。

#### 24.7 与「发布内容」的边界（重要）

- **FR-24.7.1** Terraform **只管基础设施资源，不管站点内容**。前端产物、清单、图片、APK **不得**由 Terraform 逐个对象管理。
- **FR-24.7.2** 内容发布由一条命令完成，且该命令在合并到主分支后自动执行（见 24.9）：同步产物 → 覆盖入口页与版本文件为不缓存 → 失效 CDN → 线上自检。
- **FR-24.7.3** 该命令与 Terraform 互不干扰：它只写对象，不创建或删除资源。

#### 24.8 旧脚本的去留

- **FR-24.8.1** 迁移完成后，`src/deploy/` 下的命令式资源管理脚本**删除**（首选），历史留在 git 中；仅保留内容同步所需的最小脚本。
- **FR-24.8.2** `.deploy-state.json` 中的运行时 ID 全部迁入 Terraform 输出后作废。

#### 24.9 自动触发与发布（GitHub Actions）

- **FR-24.9.1 唯一触发器**：只引入 GitHub Actions 作为触发器，不引入其他 CI/CD 平台。理由：两个仓库本就在 GitHub；私有仓库每月 2000 分钟免费且**不需绑卡**；不需要再学一套系统。
- **FR-24.9.2 凭证**：用 OIDC 换取 AWS 临时凭证，**仓库中不存放任何长期访问密钥**。
- **FR-24.9.3 内容发布全自动**（应用仓库）：合并到 `main` → 构建前端 → 结构断言 → 同步站点桶 → 失效 CDN → 线上自检。**无人工关卡**。任一步失败即中断，线上保持上一个可用版本。
- **FR-24.9.4 基础设施需人工批准**（基础设施仓库）：合并到 `main` → 逐层 `plan` → 把差异呈现出来 → **等待人工批准** → `apply`。未批准不执行。
- **FR-24.9.5 分界的理由**：内容发布是低风险且可秒级回退；基础设施（尤其 edge 层）配错就是断站，且一月可能只改一次，值得多按一下。
- **FR-24.9.6 并发控制**：同一时刻只允许一个 `apply` 运行，避免两次变更交叠把 state 改坏。
- **FR-24.9.7 只读预览**：非主分支与拉取请求只允许 `plan`，不允许 `apply`。
- **FR-24.9.8 bootstrap 例外**：L0 必须在流水线存在之前先手动执行一次，之后才由它的产物（状态桶、OIDC 信任、部署角色）支撑后续自动化。
- **FR-24.9.9 不承担制品托管**：Actions 只做触发与执行，不作为制品仓库、不长期保存构建产物。

### FR-25 隐私与安全（v4 增量）【硬性，不可降级】

- **FR-25.1 公开产物红线不变**：站点桶中的任何文件都不得含 GPS、设备序列号、原始文件名、具体拍摄时刻。
- **FR-25.2 源桶是临时区，不是仓库**：原图含完整 EXIF 与 GPS，源桶必须私有、加密、禁止任何公有访问，且只有处理函数可写。**处理成功后立即删除该原图**；失败残留由生命周期兜底清理（默认 30 天）。源桶不承担备份职责。
- **FR-25.3 手机号**：只以加盐哈希形式保存用于比对；任何日志不得出现明文手机号。
- **FR-25.4 共享密钥**：不在客户端明文落盘；泄露时可换密钥并使旧令牌失效。
- **FR-25.5 接口防护**：登录接口有失败次数限制与全局限流，防止被当成免费转码服务。
- **FR-25.6 令牌**：短期有效，不写入日志与 URL。
- **FR-25.7 签名密钥**：keystore 与口令不入库、不进任何日志。
- **FR-25.8 基础设施仓库**：私有；不得提交 state 文件、真实敏感取值、任何密钥。

## 9. 上线验收清单

**A. 客户端**
1. 荣耀 / 小米 / 三星中至少两台真机安装成功并能打开首页。
2. 全屏无地址栏；状态栏不遮挡标题。

7. 手机选 5 张照片上传，60 秒内网页端可见。

11. 白名单外的手机号无法登录。
12. 错误密钥连续尝试被限流。
13. 上传成功后 1 分钟内，源桶中对应原图**已不存在**；失败残留对象在 30 天后被生命周期清除。

**C. 基础设施即代码**
14. 基础设施仓库为**私有**，其中 0 张照片、0 个前端产物、0 个 APK、0 个 state 文件。
15. 四层各自 `init` + `validate` 通过；无 AWS 凭证时也能通过语法校验。
16. 生产环境逐层 `plan` **输出为空**。
17. 在隔离的测试前缀下从零 `apply`，能建出同等环境（不碰生产）。

19. 既有桶 / 分发 / OAC 均以**导入**方式接管，**未发生任何重建**（对比导入前后的资源 ID 与创建时间）。
20. 应用仓库中不再存在造成「双源」的资源管理配置。
21. 新仓库 README 能让人不读代码就说清四层职责与依赖方向。

**D. 自动化**
22. 改一行样式合并到主分支，5 分钟内线上生效，全程未手动执行命令。

26. 流水线与仓库中均无长期 AWS 密钥。

## 11. 技术核查与已知限制

### 11.1 本机环境实测（2026-11-10）

| 项 | 实测结果 | 影响 |
| --- | --- | --- |
| JDK | 21.0.8，架构 **x86_64**（机器为 arm64） | 安卓构建走 Rosetta，需换 arm64 JDK |
| Android SDK / adb / sdkmanager / gradle | **全部缺失** | 需新装命令行工具（§7-1） |
| Android Studio | 未安装 | 不打算装，用命令行工具 + Gradle |
| **terraform** | **未安装** | 需新装（§7-2） |
| docker | `/usr/local/bin/docker` 可用 | 可用于构建 Lambda 镜像 |
| AWS CLI / Node / ffmpeg | 2.39.6 / v22.22.2 / 8.0 | 齐备 |

### 11.2 为什么 TWA 不可行

TWA 的渲染引擎是**用户已安装的 Chrome**（通过 Custom Tabs 全屏）。目标机型里，华为（HMS，无 GMS，通常无 Chrome）、荣耀/小米/三星国行普遍预装自家浏览器，Chrome 不保证存在。缺 Chrome 时 TWA 无法全屏，甚至不可用。

WebView 壳用的是**系统 WebView**（Android System WebView 或厂商内核），所有国产机出厂即有，不依赖任何 Google 组件。代价是内核版本参差 → 必须做能力检测与降级（FR-19.7）。

### 11.3 为什么必须引入服务端

浏览器/App 若要在 S3 上写入，需要凭证。把长期 AWS 密钥打进 APK 等于公开桶写权限（APK 可被反编译），不可接受。签发临时上传地址必须有能安全持有密钥的一方 → 最小形态即「一个函数 + 一个 HTTP 端点」。

因此红线从「纯静态、无服务器」调整为「**全托管无服务器**」：无常驻进程、无数据库服务器、无用户体系、无流量时近零成本。

### 11.4 鸿蒙 NEXT 不兼容 APK

HarmonyOS 4.x 及更早兼容 Android APK；**HarmonyOS NEXT（鸿蒙 5）不再支持 APK 安装**，需独立 ArkTS 工程。

**用户已明确：华为设备不考虑鸿蒙** —— v4 不为 NEXT 做任何适配，也不把它列为风险待办。验收机型从荣耀 / 小米 / 三星中选取（见 §9-A1），这些机型的系统内核均兼容 APK。若日后确有设备升级到 NEXT，属平台变更，需另开版本处理。

### 11.5 HEIC 不能指望在服务端解

`sharp` 在 Linux 预编译版里的 HEIF/HEVC 解码支持受专利限制，通常**不可用**；v3 是靠 macOS 的 `sips` 才处理得了 HEIC。服务端没有 sips。

因此默认在**手机端完成 HEIC → JPEG 转换**（Android 10+ 原生支持 HEIF 解码），服务端只收 JPEG/PNG。

### 11.6 Lambda 打包：走容器镜像

同一处理函数既要 sharp（图片）又要 ffmpeg（视频）。ffmpeg 静态二进制约 80MB，加上 sharp 原生模块，**有触碰 250MB 未解压部署包上限的风险**。改用容器镜像（上限 10GB）一次解决，且镜像可版本化。

### 11.7 APK 不能放站点桶

v3 已踩过：部署用「整目录同步 + 删除多余」，被排除在同步之外的对象会被判为「源端已不存在」而删除。APK 若放在站点桶，每次发布都有被清掉的风险。故 APK 放**独立桶**，经同一 CDN 以单独路径暴露。

### 11.8 Terraform 接管既有资源

- `aws_cloudfront_origin_access_control` **支持 import**（Terraform 1.5+ 的 import 块，按 id）。现有 OAC `EQAKQ33RBCH5M` 可接管。
- `aws_cloudfront_distribution` 支持按分发 ID import，但导入后需逐字段把配置调到与实际一致，**直到 plan 为空**。这是全项目风险最高的一步（改错可能让线上中断）。
- 缓解：按层分步导入，每步以 plan 为空为关卡，保留回退能力。

### 11.9 ACM 证书走导入，不重建

域名 DNS 不在 Route 53，Terraform 无法自动创建验证记录（只能用 `create_route53_records = false` + 人工提供记录名，再等验证）。现有证书已 `ISSUED`、有效期至 2027-05-26，**直接导入即可完全绕开验证流程**。2027 年续期时，由于 DNS 验证记录保留在注册商侧，ACM 会自动续期，无需 Terraform 参与。

### 11.10 模块化与「plan 为空」的张力

这是分层 IaC 里最容易被忽视的坑：社区模块（尤其 CloudFront 封装模块）为通用性会注入默认值、可选资源与命名规则，接管**已存在**的资源时往往产生大量无法消除的差异。所以模块化必须向「接管既有资源」这个现实妥协：

- 需精确对齐的层（edge）→ 直接写资源或写极薄模块；
- 全新资源的层（compute）→ 放心使用封装好的模块。

这不是反对模块化，而是把模块化用在它真正降低成本的地方。

### 11.11 内容为什么不能交给 Terraform

用 `aws_s3_object` 声明每一个产物是常见但错误的做法：几百个带哈希文件名的对象会全部进入 state，每次 `plan` 都要刷新远端状态，慢且易漂移；发布变成 `apply` 后还失去了「先同步再失效」的两段式缓存策略。业界通行做法是「基础设施归 IaC，内容归同步工具」，v4 沿用这个分工。

### 11.12 导入既有资源：不需要清空任何云端资源

常见误解是「必须先删掉旧资源，否则 Terraform 的 state 对不上」。**不必**：

- `import` 的语义是**认领**：把已存在资源的标识写进 state，之后由代码描述它。不删除、不重建、不中断。
- 导入阶段的原则是**代码向现实看齐**：写完 HCL 后若 `plan` 有差异，改代码去匹配线上现状，直到差异为空。反方向（改线上配置去迁就代码）等于用 IaC 的名义做破坏性变更，属禁止动作。
- 真正需要「清掉」的是软件层：**旧部署脚本**（会与 Terraform 争抢同一批资源，造成双源）与 **`.deploy-state.json`**（其 ID 迁入 Terraform 输出后作废）。
- 桶里的 v1/v2 历史遗留对象属**数据层**，与 state 无关。清不清是独立决定，另行确认。

### 11.13 已知限制（接受）

1. 国产 ROM 的 WebView 内核版本不可控，滚动驱动动效、View Transitions 可能降级 —— 已用能力检测兜底。
2. 私有分发无法做到「全机型无感更新」，用户仍需在系统弹窗确认安装。
3. 手机号 + 共享密钥的强度上限低于正规账号体系；适用于个位数可信使用者。
4. **源桶不保留原图**（P02）：处理成功即删除，失败残留最多 30 天。因此「灾后重建」不能靠源桶，只能靠重新从手机/本机导入 —— 这是刻意用「少一个备份」换「少一处长期 GPS 存放」。
5. 原生 `FLAG_KEEP_SCREEN_ON` 走的是 App 进程，与网页 Wake Lock 不同；但安卓 13 起系统级省电策略仍可能在极低电量下忽略该标志。
6. Lambda 视频转码受 15 分钟上限约束，超长/超大视频会被拒绝而非排队重试。
7. 前端发布依赖 GitHub Actions；私有仓库额度 2000 分钟/月，耗尽后降级为本机手动执行同一套命令（O-23）。`build:web` 只需要 Node，不需要 ffmpeg。
8. Terraform 状态是单点：误删 state 不会删除云端资源，但会让代码「失去描述」，恢复靠重新 import —— 需在仓库 README 写明步骤。
